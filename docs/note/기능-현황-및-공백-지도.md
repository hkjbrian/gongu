## 2. 구현 현황 요약

| 도메인 | 상태 | 엔드포인트 |
|--------|------|-----------|
| auth | ✅ | `POST /auth/oauth2/login`, `POST /auth/store-admin/login`, `POST /auth/token/refresh` |
| user | 🟡 | `POST /users/me/stores` (프로필 수정 API 없음 — 아래 GAP-3) |
| store | ✅ | `GET /stores`, `GET /stores/{id}` |
| store-admin | ✅ | `GET /admin/users?name=` (회원 이름검색) |
| product | ✅ | admin: 목록/상세/등록/수정/삭제 · user: 목록/상세 |
| order | ✅ | 생성/내주문/상세/취소/수령 · admin: 상품별·회원별 조회, 입고 |
| payment | ✅ | `prepare`, `verify`, `webhook` (2-phase, 멱등, 만료 자동환불) |
| **notification** | ❌ | `.gitkeep`만 존재 — 전체 미구현 |

- 구현 엔드포인트 ~25개, 테스트 파일 23개(핵심 서비스·동시성 커버).
- 인프라: Docker/compose, Prometheus+Grafana, 부하테스트 자동화 완비.

### 상태 기계 (완성)
- **Order**: `RESERVED → PAID → ARRIVED → RECEIVED` / `→ CANCELLED`
- **Payment**: `PENDING → PAID → (CANCELLED|REFUNDED|FAILED)`
- **Product**: `UPCOMING → ACTIVE → (SOLD_OUT ⇄ ACTIVE) → CLOSED`

## 3. 공백 보드

### 🔴 확정 공백 · 버그 (in-scope, 조치 필요)

- **GAP-1 · 알림 도메인 전체 미구현.** 요구사항 문서에 "주문 확정/입고/취소 알림, 목록·읽음처리"가
  명시돼 있으나 코드는 `.gitkeep`뿐. 입고 완료 후 고객 통지 경로가 없음.
- **GAP-2 · PAID 주문 취소 시 PG 환불 미연동 (유력 버그).**
  `OrderService.cancelOrder()`는 도메인 규칙상 PAID→CANCELLED를 허용하고 재고는 복구하지만,
  PortOne 환불(`executePGCancel`/`payment.refund()`)을 호출하지 않음. 결제 후 취소 시 **돈이 안 돌아감.**
  자동 환불은 "주문 만료" 경로에만 존재.
- **GAP-3 · 회원 프로필 수정 API 미노출.** `User.updateProfile(name, phone)` 도메인 메서드는 존재하나
  이를 호출하는 컨트롤러 엔드포인트가 없음. 요구사항("프로필 수정 가능") 미충족.

### 🟡 일관성 · 보강 (운영 품질)

- **GAP-4 · 관리자 주문 조회에 기간/상태 필터 없음.** 상품별·회원별 조회 모두 최신순 페이징만 제공.
  "오늘 들어온 주문", "PAID만 보기" 같은 운영 조회 불가. (고객용 `/orders/me`엔 status 필터 있음 — 비대칭)
- **GAP-5 · 사용자 주도 환불 엔드포인트 없음.** REFUNDED 상태·`refund()`는 있으나 만료 자동환불만 사용.
  고객/관리자가 명시적으로 환불 개시하는 경로 부재. (GAP-2와 연결)
- **GAP-6 · 이메일 중복확인 요구사항 vs 실제 인증모델 불일치.** 요구사항엔 "이메일 중복 사전확인"이 있으나
  회원은 카카오 소셜, 관리자는 시드 계정이라 해당 API가 없음. 요구사항이 stale일 가능성 → 재검토.

### ⚪ 의도적 제외 (Non-Goal, 브리핑 확정)

- 공급자 직접 정산 / 본사↔공급자 협의(공구 개설 프로세스)
- 실시간 재고 동기화(Redis+Kafka), 추천·큐레이션, 실시간 채팅, 다중 PG, 모바일 앱

## 4. 논의 필요 — 열린 질문

1. **취소 정책**: PAID 주문 취소 시 자동 환불이 맞나, 아니면 "관리자 승인 후 환불"인가? (GAP-2 설계 선행)
2. **알림 채널**: 알림 도메인의 전달 수단은? (앱 인앱 알림 / 카카오 알림톡 / 이메일 / 웹훅) 범위 확정 필요.
3. **관리자 조회 규칙**: "모든 목록 조회는 기간·상태 필터를 지원한다"를 횡단 규칙으로 못박을지.
4. **환불 주체**: 고객 셀프 환불 vs 매장관리자 환불 처리 — 누가 개시하나?
5. **요구사항 문서 위상**: 01-requirements.md를 "사후 기록"에서 "선행 스펙"으로 승격할지,
   아니면 이 지도를 살아있는 단일 소스로 삼을지.
6. **본사/공급자**: README의 4자 비전을 언젠가 살릴지, 아니면 브리핑대로 완전히 접을지 명문화.

## 5. 정리 원칙 (합의된 방식)

- 워터폴식 대형 스펙 재작성은 하지 않는다. 견고한 코어는 즉흥 개발의 성과로 인정.
- 공백을 "설계 선행 필요(큰 것: 알림·환불정책)" vs "backfill(작은 것: 필터·프로필 API)"로 분류해 진행.
- 이 문서 + 시각 자료를 살아있는 단일 지도로 유지하며 계속 배포.

## 6. 결정 사항 (2026-07-15 논의)

- **GAP-2 취소/환불 정책 확정.** PAID 이후 사용자가 명시적으로 취소하면 PG 환불이 이어져야 한다(정책상 맞음).
  단 취소 트랜잭션 안에서 PG를 동기 호출하지 않는다 → **기존 "만료 자동환불" 보상 트랜잭션 패턴을 재사용.**
  `(트랜잭션) 주문 CANCELLED + 재고복구 + 환불의도 기록 → 커밋 → (커밋 후/비동기) PortOne 취소 → 성공 시 payment.refund() → 실패 시 재시도 + 대사`.
  실제 카드 환급 지연(영업일)은 카드망·은행 정산 주기 문제이며 서버 책임 아님. 서버는 취소 요청을 즉시 접수·전송한다.

- **알림 도메인 = 뒤로 미룸(예정), 설계 방향 확정.** 채널에 종속되지 않도록 **인앱 알림 테이블을 도메인의 기본**으로 둔다.
  이벤트(주문확정/입고/취소) 발생 시 Notification 레코드 저장 → 요구사항의 "목록 조회·읽음 처리"는 인앱만으로 충족.
  실제 전송은 **어댑터로 교체**(인앱 / 이메일SMTP / 카카오 "나에게 보내기").
  카카오 알림톡(비즈니스)은 사업자등록·채널·템플릿 심사가 필요해 로컬/개인 프로젝트에선 보류.
  단, 이미 카카오 로그인이 있으므로 카카오 메시지 API "나에게 보내기"(`talk_message`)는 사업자 없이 데모 가능.
  프론트는 `GET /notifications` 폴링(또는 SSE)으로 처리.

- **조회 필터 = 횡단 규칙으로 승격.** "모든 목록 조회(회원·관리자 공통)는 기간(from/to)·상태·페이징·정렬을 지원한다."
  공통 조회 조건 객체(예: `OrderSearchCondition`) + QueryDSL/Specification로 한 번 만들어 재사용.
  이 규칙으로 GAP-4(관리자 필터 없음) 및 고객/관리자 비대칭이 동시 해소.

- **아키텍처 = 모듈러 모놀리스 확정.** 4자 이해관계자는 배포 단위가 아니라 bounded context(역할)다.
  혼자 개발 + 로컬 실행 단계에서 마이크로서비스 이점은 없고 분산 트랜잭션 비용만 증가(특히 결제·정산).
  현행 `domain/{...}` 패키지 경계를 마이크로서비스 쪼갤 때만큼 깨끗하게 유지하며, 향후 `domain/supplier`·`domain/settlement`를 같은 방식으로 추가.
  분리 검토 신호(팀 확장, 도메인별 독립 스케일/배포)는 현재 해당 없음.

- **본사·공급자 = 다음 마일스톤.** 4자 입장을 모두 담기 위해 별도 마일스톤으로 추가 예정(모놀리스 내부 모듈로).

## 7. 결정 사항 (2026-07-15 논의, 이어서)

### 모듈 분리의 의미 — "Order가 Payment를 부르는 건 당연"이 맞음
- 모듈 규율은 호출 자체를 금지하는 게 아니라 **의존 방향과 대상(무엇에 의존하는가)**을 다룬다.
- **패키지 = 폴더(경계는 약속)**, **모듈 = 공개/은닉이 강제되는 단위**. 지금은 패키지만 있는 상태.
- **구체적 위험(GAP-2에서 실제로 마주침)**: 현재는 `Payment → Order` 한 방향(결제완료 시 주문 PAID).
  취소 시 환불을 구현하면 `Order → Payment`가 생겨 **양방향 순환(cycle)** 발생.
  순환 → 독립 테스트 불가, 트랜잭션 소유 모호, 변경 파급 예측 불가(진흙 공).
- **해법**: 반대 방향은 **이벤트로**. 예) Order가 "OrderCancelled" 발행 → Payment가 구독해 환불.
  방향은 `Payment → Order` 하나로 유지. 만료 자동환불 보상 패턴과 동일 모양.
- **모듈 분리 이점 4가지**: ① 순환 방지 ② 독립 테스트 ③ 교체 가능성(PG/알림 채널) ④ 변경 파급 통제.
- **지금 할 것(솔직한 최소선)**: Spring Modulith/JPMS 같은 무거운 도구는 아직 불필요.
  ⓐ 의존은 한 방향 + 반대는 이벤트, ⓑ 남의 **내부**가 아니라 **정해진 진입점(퍼사드)**에만 의존 — 이 두 습관만.

### 화면 스케치 = 부가기능 발굴 도구 (우선순위 확정)
- API·도메인 관점만으론 **"시스템이 지켜야 하는 것"**(상태전이·정합성·환불)만 나온다.
  **"있으면 좋은 것"**(인기순위·마감임박·검색·찜·재입고알림)은 화면/여정을 그려야 나온다 — 종류가 다른 요구사항.
- **우선순위**: ① 🔴 확정 공백 정리(화면 없이 진행) → ② 화면 스케치로 조회 부가기능 발굴(공통 필터 규칙에 합류) → ③ 본사·공급자 마일스톤.
- 발굴엔 정교한 디자인보다 **저해상도 와이어프레임**이 유리. 클로드가 Artifact로 직접 생성.
  가장 발굴이 많은 지점은 **고객 상품목록 화면**(정렬·필터·뱃지·검색이 전부 여기서 나옴).
- 산출물: `고객 여정 → 매장 관리자` 순서 와이어프레임(별도 Artifact). 화면 위 번호 주석으로 발굴 후보 표기.
