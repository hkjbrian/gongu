# ADR-008 부록: 결제 장애 수렴 매트릭스

- 작성일: 2026-09-13
- 기준 코드: `origin/main` `ca13c73` — 작성 시점 로컬 `main`은 14커밋 뒤처져 있었다(#222 미반영). 로컬 체크아웃 기준으로 읽지 않는다
- 관련: ADR-007(`payment_만료_취소_설계.md`), ADR-008(`결제_확정_아키텍처.md`), ADR-005(`재고_동시성_제어_전략.md`)

## 목적

돈이 걸린 흐름의 **단계 × 장애**마다 "그 순간 남는 상태 → 누가 수렴시키나 → 최종 상태 → 무엇으로 검증했나"를 적는다.
현재 보장 수준과 목표 상태를 함께 적어 두 가지 용도로 쓴다.

1. ADR-008 이행 체크리스트 — 어느 칸이 어떤 이슈로 닫히는지
2. 장애 주입 테스트 목록 — 각 행이 하나의 시나리오

## 지켜야 할 불변식

| ID | 불변식 |
|---|---|
| I1 | PG에서 돈이 움직인 결제는 어떤 단일 장애 뒤에도 결국 우리 DB에서 **PAID(이행)** 또는 **REFUNDED**로 끝난다 |
| I2 | PG에서 돈이 움직이지 않은 결제는 결국 **CANCELLED** 또는 **FAILED**로 끝나고, 잡았던 재고 예약이 풀린다 |
| I3 | 결과를 **모르는** 동안에는 결제를 닫지 않는다 (모름 ≠ 실패) |
| I4 | 모든 상태 전이와 그 근거(PG 응답)가 이력으로 남는다 |

## 범위와 전제

- 단일 서버 인스턴스. 다중 인스턴스(스케줄러 중복 실행, 서킷 상태 공유)는 범위 밖
- 카드 결제(동기 승인)만. 가상계좌 등 비동기 결제수단은 범위 밖
- 결제 완료 후 사용자 환불 요청 기능은 없다 — `Order.cancel()`은 RESERVED에서만 허용
- 재고 쪽 Redis–MySQL 불일치 자체는 ADR-005·재고 이슈(#188, #189, #228)에서 다룬다. 이 문서는 결제와 만나는 지점만 적는다

## 0. 흐름과 현재 수렴 장치

**흐름 단계**

| 단계 | 내용 | 코드 |
|---|---|---|
| S1 | 주문 예약 — Redis `DECR` + 주문 RESERVED | `OrderService.createOrder` |
| S2 | 결제 준비 — 결제 PENDING 행 생성 | `PaymentService.preparePayment` |
| S3 | **PG 승인 — 브라우저와 PG 사이에서 돈이 움직인다. 서버는 참여하지 않는다** | — |
| S4 | 확정 트리거 도착 — verify / 웹훅 / 만료 스케줄러 | `PaymentController`, `PaymentExpiryScheduler` |
| S5 | 확정 반영 — 결제·주문 행 비관적 락 → PG 조회 → PAID → `confirmStock` | `PaymentService.completePayment` |
| S6 | 보상 — PG 취소 → REFUNDED (주문 만료 후 도착, 금액 불일치) | `completePayment`의 CANCELLED 분기·금액 불일치 분기 |

**현재 수렴 장치**

| 장치 | 동작 | 한계 |
|---|---|---|
| verify | 사용자가 결제창을 닫을 때 호출 | 사용자 행동에 의존. 판정 불가 시 503만 받아 결과를 모름(#216) |
| 웹훅 + PG 재시도 | 비2xx 응답이면 PG가 재전송 | **현재 유일한 "다시 확인" 장치.** PG 재시도 정책에 의존(§7) |
| `PaymentExpiryScheduler` | 1분 주기. PENDING 결제 + RESERVED 주문이 TTL(10분) 지나면 결제 CANCELLED·주문 취소·Redis 예약 해제 | **PG에 묻지 않고 닫는다**(#215). TTL 10분 < PortOne 세션 15분(#205) |
| `OrderExpiryScheduler` | PENDING 결제가 없는 만료 주문 취소·예약 해제 | — |
| ADR-007 보상 | 취소된 주문에 결제 트리거가 오면 PG 취소 → REFUNDED | 트리거가 도착해야 동작 |
| 즉시 방어(#213·#214·#222) | PortOne 타임아웃 2s·재시도 3회(최악 ≈7s)·서킷 브레이커·`completePayment` 벌크헤드 20 | 번짐 범위를 제한할 뿐, 락 안 PG 호출(#146)은 그대로 |
| 재고 동기화 | `StockSyncRunner`(재기동), `StockReconciliationScheduler`(5분, 과소만 복구) | 과다 미복구(#189) |
