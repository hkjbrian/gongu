# ADR-008: 결제 확정 아키텍처

- **날짜**: 2026-09-07
- **상태**: 제안됨 (초안)
- **이슈**: #146, #209, #213, #215, #216, #219
- **관련 ADR**: ADR-005(재고 동시성), ADR-007(Payment 만료 취소), 웹훅 서명 검증 전략(#208), 결제·주문·PG 상태 전이 분석(PR #140)

---

## 배경

`completePayment()`는 세 경로(사용자 `verify`, PortOne `webhook`, 향후 만료 스케줄러)에서
호출되는 결제 확정의 단일 진입점이다. PR #139/#140에서 상태 전이·보상 트랜잭션을 정교하게
다듬었고, #207에서 "판정 불가 vs 판정 완료"를 분리했으며, #208에서 웹훅 서명 검증을 붙였다.

그러나 확정 경로의 **구조**는 초기 구현 이후 바뀌지 않았다. `성능 개선 & 모니터링` 마일스톤에
쌓인 결제 이슈(#146, #209, #213, #215, #216, #219)는 개별 버그·개선으로 보이지만,
실제로는 **하나의 구조적 원인**에서 파생된다. 이 ADR은 그 구조를 기술하고, 업계 표준 결제
확정 패턴과 대조해 목표 아키텍처와 이행 순서를 정한다.

이 문서는 `#146`을 단독으로 판단하지 않기 위해 작성한다. #146의 "PG 호출을 트랜잭션 밖으로"는
목표 아키텍처의 한 조각일 뿐이고, 같은 패턴을 #215가 다시 요구하며, #216/#209/#219가
그 위에 얹힌다.

## 1. 기존 아키텍처

### 1.1 확정 경로

```
                         ┌─────────────────────────────┐
  POST /payments/verify ─┤                             │
  (브라우저, 결제창 완료 후)│                             │
                         │   PaymentService            │
  POST /payments/webhook ┤   .completePayment(id)      │──▶ PortOne getPayment/cancel
  (PortOne Transaction.  │   @Transactional            │
   Paid, #208 서명검증)   │   (noRollbackFor=Business,  │──▶ MySQL payments / orders / products
                         │    Infra)                   │
  (예정) 만료 스케줄러 #215 ┤                             │
                         └─────────────────────────────┘
```

세 경로가 **하나의 `@Transactional` 메서드**로 수렴한다.

### 1.2 `completePayment()` 트랜잭션 한 개가 하는 일

| 순서 | 작업 | 자원 |
|---|---|---|
| 1 | `findByMerchantUidWithLock(paymentId)` | payments 행 **비관적 쓰기 락** |
| 2 | `payment.status == PAID` → 조기 반환 (멱등) | — |
| 3 | `findByIdWithLock(order.id)` | orders 행 **비관적 쓰기 락** |
| 4 | order.CANCELLED 분기 → `executePGCancel()` | **외부 HTTP** (락 2개 보유 중) + refund/expire |
| 5 | `portOneClient.getPayment(paymentId)` | **외부 HTTP** (락 2개 보유 중) |
| 6a | 금액 일치 → `order.pay()` + `payment.confirm()` | |
| 6b | ↳ items 루프: `findByIdWithLock(product.id)` + `confirmStock()` | products 행 **비관적 쓰기 락 × N** |
| 7 | 금액 불일치 → `executePGCancel()` + `payment.refund()` + `order.cancel()` + Redis `releaseStock` 루프 | **외부 HTTP** (락 보유 중) |

전체가 한 트랜잭션이며, 5·7·4단계에서 **비관적 락 2개(+products N개)를 쥔 채 외부 HTTP를
호출**한다.

### 1.3 동시성 제어

- **전면 비관적 락.** ADR-005("공구 오픈은 충돌이 정상 상황")의 방침을 결제 경로까지 계승.
- `@Version`은 `Product`에만 존재하고 보조 안전망 역할. `Payment`·`Order`에는 없다.
- 데드락 방지: 모든 경로가 `Payment → Order → Product` 순서로 락 획득 (ADR-007).

### 1.4 멱등·재시도·복원력

- 멱등: `payment.status == PAID` 조기 반환 + `@Transactional(noRollbackFor = ...)`로
  예외를 던져도 상태 커밋.
- 재시도: `PortOneClient`에 `@Retry`(max 3) + `@CircuitBreaker` — **단 #213으로 현재 미작동**
  (aspect 순서 버그로 논리 호출당 HTTP 1회).
- 웹훅 무한 재시도 방지: 터미널 에러코드에 HTTP 200 반환 (#207).
- PG 판정 불가 시 `PENDING` 유지 (#207).

### 1.5 만료

- TTL 20분(ADR-007) — **설정은 10분, #205 불일치**.
- 스케줄러 2개: `PaymentExpiryScheduler`(PENDING Payment 있는 만료 Order),
  `OrderExpiryScheduler`(PENDING Payment 없는 만료 RESERVED Order).
- `PaymentExpireService.cancelExpiredPayment()`는 **PG와 통신하지 않는다** —
  "PENDING이면 PG에 카드 정보 미제출이므로 취소할 세션이 없다"는 전제.

## 2. 기존 아키텍처에서 발생하는 문제점

### P1. 외부 호출이 트랜잭션 + 비관적 락 안에 있다 — 커넥션 풀·락 결합

`completePayment()`는 payments·orders 행 락과 DB 커넥션을 쥔 채 PortOne HTTP를 호출한다.

**커넥션 풀 산술** (리틀의 법칙, `L = λ × W`)

- HikariCP `maximum-pool-size = 25`, `minimum-idle = 25`, `connection-timeout = 30s`
- verify 도착률 λ, PG 응답 시간 W ≈ D
- 동시 커넥션 점유 `L ≈ λ · D`
- 예: λ = 10 req/s, D = 3s → L ≈ 30 > 25 → **풀 고갈**, 31번째 요청은 30초 후
  `SQLTransientConnectionException`
- #213을 고치면 최악 W = 3 × (read-timeout 5s + wait 0.5s) ≈ **16.5s** → λ = 2 req/s만
  되어도 고갈

**추가 악화**

- 트랜잭션이 길수록 데드락 확률 증가, `products` 행 락(6b)이 주문 생성 경로(ADR-005
  비관적 락)와 교차해 락 대기가 상호 전파
- PG 부분 장애(5xx)면 서킷이 보호하지만, 완전 장애(무응답)는 #214 이전엔 서킷 집계도 안 됨
  → 모든 요청이 타임아웃을 그대로 소진

**업계 근거**

- "Holding a transaction open for the duration of an external call ... increasing the
  likelihood of connection pool exhaustion" — 트랜잭션 경계 안 API 호출은 회피 대상 안티패턴
- 토스페이먼츠: MySQL에 `PaymentTransaction`을 `PROCESSING`으로 **먼저 기록**한 뒤 승인 API 호출
- 반론도 있다(Rock the JVM): "트랜잭션 밖으로 빼기"만으로는 부족하며, 프로세스가 죽으면
  식별자가 유실돼 재시도가 안 된다 → outbox 필요. **단 우리는 재조회 모델**이라
  `paymentId`가 DB에 남고 스케줄러가 재수렴하므로 이 위험은 낮다(→ D1에서 활용).

### P2. `verify`와 `webhook`이 같은 행 락을 두고 경쟁

정상 흐름에서 **거의 항상** 발생한다. 사용자가 결제창을 닫고 `verify`를 호출하는 시점과
PortOne이 `Transaction.Paid` 웹훅을 보내는 시점이 겹친다. 둘 다 같은 `paymentId`로
`completePayment()`에 진입한다.

- 먼저 진입한 쪽이 `findByMerchantUidWithLock`으로 락을 잡고 PG 응답(D초)을 기다린다
- 나머지 한 쪽은 그 D초 동안 락 획득 대기
- Stripe도 "`fulfill_checkout` might be called multiple times, possibly concurrently"라고
  명시하지만, 해법으로 **멱등**을 요구한다 — 락으로 직렬화하지 않는다

### P3. 확정 트랜잭션이 너무 많은 일을 한다

PG 확정과 **재고 이행**(MySQL `confirmStock` + Redis `releaseStock` + 카운터)이 한
트랜잭션에 묶여 있다.

- 트랜잭션 시간·락 범위가 재고 로직만큼 더 늘어난다
- `products` 행 락이 주문 생성 경로와 교차 (P1 참조)
- 재고 차감 실패가 결제 확정 롤백을 유발 — 돈은 이미 PG에서 승인됐는데

### P4. 만료 경로에 PG 확인이 없다 (#215) — 가장 비싼 사고 유형

`PaymentExpireService`는 PG에 묻지 않고 `payment.expire()` + `order.cancel()`을 실행한다.

**시나리오**: 사용자가 결제를 완료(카드 승인됨) → `verify`가 PG 조회 실패로 `PENDING` 유지
(#207 동작대로) → 웹훅도 유실 → TTL 경과 → 스케줄러가 PG 확인 없이 취소.

**최종 상태: PG=PAID, DB=CANCELLED, 환불 없음.** 고객 돈이 나갔고 주문은 사라졌다. 자동
복구 경로가 없다.

#215가 이를 고치려면 "취소 전 PG에 한 번 물어본다"가 필요한데, 그러면 **스케줄러 트랜잭션
안에서 PG를 호출**하게 되어 P1이 스케줄러로 확산된다. #215 본문도 "조회를 트랜잭션 밖에서
수행하고 결과만 짧은 트랜잭션으로 반영할 것"이라고 명시 — **#146과 같은 패턴을 요구**한다.

### P5. 미결(PENDING) 결과를 클라이언트가 알 수 없다 (#216)

#207 이후 PG 조회 실패 시 `PENDING` 유지는 옳지만, `verify`가 비2xx를 반환하면 클라이언트는
실패로 간주하거나 `verify`를 반복 호출한다. 후자는 **매 호출이 PG 조회를 유발**한다.
결제 상태를 조회하는 읽기 전용 경로가 없다.

### P6. 상태 이력이 없다 (#209)

상태 변경이 `payments` 단일 행 `UPDATE`로만 반영된다. "이 결제가 왜 FAILED가 되었는지"를
코드 경로 추론으로만 판단해야 한다 (#207 조사 때 실제로 겪음). PG 응답 원문도 버린다 →
분쟁 시 대조할 근거 없음.

### P7. 유효 웹훅 재전송을 막지 못한다 (#219)

#208의 타임스탬프 검사(±300초)는 freshness 검사일 뿐, 창 안에서 캡처된 유효 웹훅의
재전송은 막지 못한다. `webhook-id`를 저장하지 않으므로 `PENDING` 상태에서 PG 재조회를
반복 유발할 수 있다.

### 문제점 → 이슈 매핑

| 문제 | 이슈 | 성격 |
|---|---|---|
| P1 외부 호출이 락 안에 | #146 | 구조 |
| P1 재시도 미작동 | #213 | 선행 버그 |
| P2 verify/webhook 락 경쟁 | #146 | 구조 |
| P3 확정 트랜잭션 과부하 | (신규) | 구조 |
| P4 만료 경로 PG 미확인 | #215 | 사고 |
| P5 미결 결과 조회 불가 | #216 | 기능 |

## 3. 업계 표준 결제 확정 패턴

리서치(Stripe / 토스페이먼츠 / Mollie / 우아한형제들·카카오페이 기술블로그)에서 반복되는
7가지 패턴. 이 프로젝트는 이미 대부분을 이슈로 인지하고 있다.

| # | 패턴 | 근거 | 현재 |
|---|---|---|---|
| 1 | **웹훅이 이행 트리거, 리다이렉트/verify는 UX** | "결제 후 인터넷이 끊겨 랜딩페이지에 못 와도 이행은 보장돼야 한다. redirect는 결제 증거가 아니다" (Stripe) | #216 하이브리드로 부분 채택 |
| 2 | **웹훅 = ID만, 상세는 PG API 재조회** (Mollie 패턴) | "provider API에서 가져오므로 진위가 내재적으로 검증된다" | PortOne V2가 이 구조. 현 코드도 이대로 |
| 3 | **이행 함수는 멱등** — 여러 번·동시 호출 안전 | "`fulfill_checkout` might be called multiple times, possibly concurrently" (Stripe) | 락으로 직렬화 중 (P2) |
| 4 | **이벤트 멱등** — event-id 저장·스킵 | Stripe / Standard Webhooks | #219 |
| 5 | **웹훅만으론 부족 — 조정(reconciliation) 배치** | "웹훅도 메시지라 지연·중복·유실된다. 완벽한 처리에도 매일 대사하라" | #215가 겸할 수 있음 |
| 6 | **append-only 상태 이력 / 원장** | "돈이 오간 기록은 덮어쓰지 않고 쌓는다" | #209 |
| 7 | **확정 트랜잭션은 짧게, 외부 호출·후속 이행은 밖으로** (아웃박스/사가) | 카카오페이 MSA 트랜잭션 | #146, P3 |

핵심 통찰: **확정 경로가 하는 일은 "명령"이 아니라 "조회"다.** 브라우저가 `verify`를
호출하는 시점에 카드 승인은 이미 끝났고, 서버는 PG에 기록된 결과를 읽어 반영할 뿐이다
(#216의 판단). 그래서 완전한 비동기 큐는 이 도메인에 과하고, **짧은 조회 + 조건부 반영 +
조정 배치**의 조합이 맞다.

## 4. 결정 (제안)

### D1. PG 조회를 트랜잭션·락 밖으로 — 3경로 공통 컴포넌트

`PaymentReconciler.reconcile(paymentId)` 도입. verify·webhook·만료 스케줄러(#215)가 모두 호출.

```
1. (락 없음, readOnly) payment 조회
     - 터미널 상태(PAID/FAILED/REFUNDED) → 즉시 결과 반환
2. (트랜잭션 없음, 커넥션 미보유) portOneClient.getPayment(paymentId)
3. 짧은 쓰기 트랜잭션: 조건부 UPDATE로 상태 반영 (D2)
```

- P1(커넥션·락 결합), P2(락 경쟁), P4(#215 확산)를 한 번에 해소
- 재조회 모델이므로 2·3단계 사이에 프로세스가 죽어도 `paymentId`는 DB에 있고 조정 배치가
  재수렴 → outbox 없이도 안전 (Rock the JVM 반론이 우리에겐 약하게 적용)

### D2. 확정을 조건부 UPDATE(guarded write)로 — Payment/Order 비관적 락 제거

```sql
UPDATE payments SET status='PAID', amount=?, paid_at=?
 WHERE merchant_uid=? AND status='PENDING';        -- affected 0 → 경쟁에서 짐 → 재조회 후 분기

UPDATE orders   SET status='PAID'
 WHERE id=? AND status='RESERVED';                 -- affected 0 → 이미 취소/결제됨 → 보상 경로
```

- `paymentId`·`orderId`당 동시 writer는 사실상 2명(verify + webhook, 또는 pay + 스케줄러)
  → **충돌 희소** → 낙관적/조건부 제어가 적합. ADR-005의 재고(단일 row에 수십~수백 동시
  요청, 충돌 빈번)와 **정반대 상황**이다
- #146이 요구하는 "TX2 재검증"이 `WHERE` 절에 원자적으로 들어감 → 트랜잭션 분리보다
  추론이 쉽다
- `@Version` 병행도 가능하나 조건부 UPDATE가 더 명시적
- **⚠️ 측정으로 확인 후 확정한다.** ADR-005 #187에서 낙관적 락은 고충돌 시 붕괴했다
  (100 RPS 실패율 55%, HikariCP 타임아웃 6,634건). 결제 확정은 저충돌이라 반대 결과가
  예상되지만, 근거 없이 채택하지 않는다 (5절 실험 계획)

### D3. 재고 이행을 확정 트랜잭션에서 분리 (별도 이슈)

- 확정 트랜잭션: `payment.PAID` + `order.PAID`만 커밋
- 재고 차감(`confirmStock`)·Redis 해제·카운터·알림: `@TransactionalEventListener(AFTER_COMMIT)`
  또는 outbox 이벤트
- 범위가 크고 재고 도메인(ADR-005)과 얽히므로 **별도 이슈로 분리**. 단 D2와 정합하게 설계

### D4. verify 하이브리드 응답 (#216 채택)

```
POST /payments/verify
  → 200  결제 확정                     (정상 — 대부분)
  → 202  { status: PENDING, statusUrl: "/payments/{id}/status" }   (판정 불가)

GET /payments/{id}/status  → { status }   (본인 결제만, 읽기 전용, PG 미호출)
```

- 비동기 작업 큐는 도입하지 않는다 (#216 근거: 조회지 명령 아님, 정상 응답 수백 ms)

### D5. 웹훅 신뢰 경계 정리 (#208 완료 + #219)

- 서명 검증(#208) + `webhook-id` 원자적 저장·중복 차단(#219, Redis `SET NX` 또는 DB 유니크)
- 웹훅은 여전히 **트리거**다. payload에 amount가 없으므로 source of truth는 `getPayment` 응답
  (패턴 2). #219로 재전송이 PG 재조회를 유발하는 경로(P7)를 닫는다

### D6. 상태 이력 append (#209)

- `payment_events` 테이블: `payment_id, from_status, to_status, trigger, reason,
  pg_raw_response(마스킹), created_at`
- 기록 지점: D1 컴포넌트가 상태를 반영하는 자리에서 함께 기록 (경로 단일화의 부수 효과)
- PG 응답 원문 확보는 #208의 원문 바디 확보와 같은 성격 → 함께

## 5. 실험 계획 — 기존 설계 vs 조건부 UPDATE

`#146`/`#187`의 방법론(시나리오별 `duration`으로 처리량 산출, 판독 오류 주의)을 따른다.

**선행**: #213(@Retry 미작동)을 먼저 고치거나, 전/후 둘 다 측정한다. before 수치가
재시도 동작 여부에 크게 좌우된다.

**하네스**: `load-test/scenarios/02-pg-latency.js`(PG 지연 중 커넥션 홀딩 관찰),
`04-circuit-breaker.js`(PG 500), `03-scheduler-webhook-race.js`(경쟁 정확성 회귀).
Mock PG `delayMs`로 PG 지연 스윕(0.5s / 3s / 10s / timeout).

**측정 지표**

| 지표 | 출처 |
|---|---|
| `hikaricp_connections_pending` peak | Prometheus |
| `hikaricp_connections_acquire` p95/max | Prometheus |
| `gongu.db.lock.query_duration` (신규 태그: entity=payment) | Micrometer |
| InnoDB row lock wait (`innodb_row_lock_time_avg`) | MySQL |
| `/payments/verify` p95·p99·실패율, 안정 처리량 | k6 |
| `OptimisticLock`/조건부 UPDATE 미스 카운트 (신규) | Micrometer |

**핵심 산출물**: PG 지연(x축) vs verify p95 / HikariCP pending(y축) 곡선.
비관적 락은 선형 악화, 조건부 UPDATE는 평탄 — 이 대비가 "무엇이 나아졌는지"를 한 장으로 보여준다.

**판정 기준**: 조건부 UPDATE가 (a) 동일 부하에서 HikariCP pending·verify p95를 유의미하게
낮추고 (b) `03-scheduler-webhook-race`에서 더블 컨펌·환불 누락 0건이면 채택.
그렇지 않으면 D1만 적용하고 비관적 락 유지(#146의 원안).

## 8. 결과

**긍정적 영향**

- 확정 경로 3개가 한 컴포넌트(D1)로 수렴 → 로직 중복·누락 위험 감소
- 커넥션 풀과 PG 지연의 결합 해소 (P1) → PG 장애가 나머지 API를 마비시키지 않음
- verify/webhook 락 경쟁 소멸 (P2)
- #215의 "가장 비싼 사고"에 자동 복구 경로 생김 (P4)
- 상태 이력으로 사후 분석·분쟁 대응 가능 (P6)

**부정적 영향 및 제약**

- 조건부 UPDATE는 비관적 락보다 "코드로 강제되는 순서"가 약함 → 상태 전이 가드를 도메인
  메서드에 계속 의존. 테스트로 커버 필요
- D1/D2/D6가 상태 전이 로직을 건드림 → PR #140에서 잡은 6개 엣지 케이스 회귀 테스트 필수
- 컴포넌트 1개가 3경로의 SPOF가 됨 (기존엔 메서드 1개였으니 실질 동일하나 명시)

**향후 고려**

- 비동기 결제수단(가상계좌 등) 추가 시 D4의 202 경로가 주 경로가 됨 → 재설계
- 다중 인스턴스 배포 시 서킷 상태·스케줄러 락(#145 ShedLock 계열) 별도 검토
- 상태 전이를 명시적 State Machine으로 (ADR-007이 "현재 규모에선 오버엔지니어링"으로 보류)
