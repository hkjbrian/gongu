# ADR-002: 아키텍처 및 코딩 룰

- **날짜**: 2026-04-19
- **상태**: 승인됨

---

## 배경

Gongu는 동시성 제어(재고 차감, 주문 충돌), PG 결제 연동, 서킷브레이커 등 기술적으로 복잡한 요구사항을 포함하는 프로젝트다. 개인 프로젝트로서 이 기술 구현이 주요 목표이기 때문에, 아키텍처 선택이 개발 속도와 코드 품질에 직접적인 영향을 미친다.

다음 두 가지를 결정해야 했다.

1. **전체 아키텍처 스타일**: 레이어드(Layered) vs 헥사고날(Hexagonal) 중 어느 것을 선택할 것인가?
2. **코딩 룰**: 도메인 모델을 어떻게 설계할 것인가? 레이어 간 책임을 어떻게 나눌 것인가?

---

## 결정

### 아키텍처: 3-Layered Architecture 채택

```
Controller  →  Service  →  Repository
   (HTTP)     (유스케이스)    (JPA/DB)
```

### 코딩 룰: Rich Domain Model 적용

엔티티(Entity)는 단순 데이터 컨테이너(Anemic Domain Model)가 아니라, 도메인 규칙과 상태 전이 로직을 스스로 캡슐화하는 풍부한 객체(Rich Domain Model)로 설계한다.

---

## 검토한 대안

### 아키텍처 대안 1: 헥사고날 아키텍처 (Hexagonal Architecture)

포트(Port)와 어댑터(Adapter)로 도메인과 인프라를 완전히 분리하는 구조다.

**장점**
- 도메인 로직이 인프라(JPA, 외부 API 등)에 의존하지 않아 테스트가 용이하다.
- 인프라 교체 시 도메인 코드를 수정할 필요가 없다.

**단점**
- 포트 인터페이스, 어댑터 클래스, 유스케이스 클래스 등 보일러플레이트가 대폭 증가한다.
- 개인 프로젝트에서 DB나 외부 API를 교체할 가능성이 낮으므로 실질적인 이득이 적다.
- 기술 구현(동시성 제어, 결제 등) 자체가 목표인 프로젝트에서 구조적 오버헤드가 개발 속도를 저하시킨다.
- 헥사고날의 핵심 이점인 "도메인과 인프라 분리"는 Rich Domain Model 룰만으로도 일부 달성 가능하다.

**결론**: 제외. 단, Rich Domain Model 규칙을 적용하여 헥사고날 아키텍처의 핵심 이점을 부분적으로 확보한다.

---

### 아키텍처 대안 2: 3-Layered Architecture (채택)

Controller → Service → Repository의 3계층 구조다. Spring 생태계에서 가장 보편적인 패턴이다.

**장점**
- 진입 장벽이 낮고 추가 보일러플레이트가 없어 개발 속도가 빠르다.
- 기술 복잡도(동시성, 결제, 서킷브레이커)에 집중할 수 있다.
- Rich Domain Model 룰을 함께 적용하면 서비스 레이어 비대화(Fat Service)를 방지할 수 있다.

**단점**
- 규칙 없이 사용하면 서비스 레이어에 모든 비즈니스 로직이 집중되어 유지보수가 어려워진다(이 문제는 Rich Domain Model 룰로 해결).

**결론**: 채택.

---

### 코딩 룰 대안 1: Anemic Domain Model

엔티티는 필드와 getter/setter만 가지고, 모든 비즈니스 로직은 Service에 위치하는 방식이다.

**단점**
- 서비스 레이어가 비대해지고, 동일한 규칙이 여러 서비스에 중복된다.
- 엔티티의 불변식(Invariant)을 보장하기 어렵다. 외부에서 setter를 통해 잘못된 상태로 만들 수 있다.
- 도메인 규칙이 흩어져 있어 파악과 수정이 어렵다.

**결론**: 제외.

---

### 코딩 룰 대안 2: Rich Domain Model (채택)

엔티티가 자신의 상태 전이 로직과 불변식 검증을 직접 책임지는 방식이다. Tell, Don't Ask 원칙을 따른다.

**장점**
- 도메인 규칙이 엔티티 안에 응집되어 중복이 줄어든다.
- 엔티티가 항상 유효한 상태를 유지한다(불변식 보호).
- 서비스 레이어는 유스케이스 조율에 집중하고 세부 규칙은 엔티티에 위임한다.

**결론**: 채택.

## 결과

### 레이어별 책임

| 레이어            | 책임                                                      |
|----------------|---------------------------------------------------------|
| **Controller** | HTTP 요청/응답 처리, 입력 유효성 검증(`@Valid`), DTO ↔ 도메인 변환        |
| **Service**    | 유스케이스 조율, 트랜잭션 경계(`@Transactional`) 관리, 여러 엔티티·레포지토리 조합 |
| **Repository** | 데이터 접근(Spring Data JPA), 복잡한 조회 쿼리(JPQL / QueryDSL)     |
| **Entity**     | 도메인 규칙 캡슐화, 상태 전이 메서드, 불변식(Invariant) 검증                |

---

### 금지 사항

**Entity에서 금지**
- `public setter` 사용 금지. 상태 변경은 반드시 의미 있는 도메인 메서드를 통해서만 한다.
- DB 조회(Repository 주입), 외부 API 호출, 트랜잭션 관리 금지.
- `@Transactional` 어노테이션 사용 금지.

**Service에서 금지**
- 엔티티 내부 상태를 getter로 꺼내어 Service에서 직접 판단하는 비즈니스 로직 금지.  
  예: `if (product.getStock() > 0) { product.setStock(product.getStock() - quantity); }` 형태 금지.

---

### 코드 예시: 재고 차감 케이스

#### Rich Domain Model (채택 패턴)

```java
// Product.java — 도메인 규칙을 스스로 캡슐화
@Entity
public class Product {

    private int stock;

    // public setter 없음. 상태 변경은 도메인 메서드를 통해서만.
    public void decreaseStock(int quantity) {
        if (this.stock < quantity) {
정            throw new BusinessException(ProductErrorCode.INSUFFICIENT_STOCK);
        }
        this.stock -= quantity;  // 불변식 검증 후 상태 변경
    }
}

// OrderService.java — 유스케이스 조율에만 집중
@Service
@Transactional
public class OrderService {
    public void placeOrder(Long productId, int quantity) {
        Product product = productRepository.findByIdWithLock(productId).orElseThrow();

        // 엔티티에게 작업을 위임 (Tell, Don't Ask)
        product.decreaseStock(quantity);

        // 이후 주문 생성, 이벤트 발행 등 유스케이스 조율
    }
}
```

---

### 후속 조치

- 모든 Entity는 `@Setter`(Lombok) 또는 `public setXxx()` 메서드 작성 금지. 빌더 패턴 또는 정적 팩토리 메서드로 생성한다.
- Entity의 상태 전이 메서드는 불변식 위반 시 ADR-004(예외 처리 전략)에 따라 `BusinessException` 또는 그 하위 클래스를 던진다.
- 서비스 레이어 코드 리뷰 시 getter 체이닝 후 setter 호출 패턴을 발견하면 리팩터링 대상으로 간주한다.
- 낙관적 락(`@Version`)이나 비관적 락을 사용하는 동시성 제어 케이스에서도 이 원칙을 유지한다. 락 획득 후 엔티티 메서드를 호출하는 방식으로 구현한다.

## 여러 엔티티에 걸친 로직 처리 기준

### 핵심 원칙

> Service는 "누가 뭘 할지" 조율만 한다. 판단과 상태 변경은 항상 해당 엔티티가 직접 수행한다.

---

### Case 1: 각 엔티티가 자신의 영역만 처리 (가장 흔한 경우)

Service가 각 엔티티에게 Tell하는 방식으로 조율한다.

```java
// OrderService.java
product.decreaseStock(quantity);           // Product가 자신의 재고를 직접 차감
Order order = Order.create(user, product, quantity);  // Order가 자신을 생성
```

---

### Case 2: A 엔티티가 B 엔티티의 값을 기준으로 판단해야 할 때

B를 파라미터로 넘겨 A가 직접 판단한다. Service가 getter로 꺼내서 직접 비교하는 방식은 금지한다.

```java
// BAD — Service가 getter로 꺼내 직접 비교
if (order.getTotalPrice() > user.getCreditLimit()) { ... }

// GOOD — B(order)를 파라미터로 받아 A(user)가 직접 판단
user.validateCanAfford(order);
```

---

### Case 3: 어느 엔티티에도 속하지 않는 복잡한 계산

Domain Service 패턴을 사용한다. Domain Service는 인프라 의존이 없는 순수 계산 객체다.

- **Application Service**(우리의 `@Service`): DB 조회, 외부 API 호출, 트랜잭션 관리를 담당한다.
- **Domain Service**: DB 조회, 외부 API 호출 없이 순수 도메인 계산만 수행한다.

```java
// SettlementCalculator.java — Domain Service 예시
public class SettlementCalculator {
    public SettlementResult calculate(Order order, Product product, Store store) {
        // 인프라 의존 없이 순수 계산만 수행
    }
}
```

---

### 판단 기준 요약표

| 상황                     | 해결책                        |
|------------------------|----------------------------|
| 단일 엔티티의 상태 변경/검증       | 해당 엔티티의 메서드                |
| A가 B 기준으로 판단           | B를 파라미터로 받아 A가 판단          |
| 여러 엔티티 조율              | Service가 각 엔티티에 위임하며 흐름 조율 |
| 어느 엔티티에도 속하지 않는 복잡한 계산 | Domain Service             |

## Entity 생성 규칙

**결정**: 정적 팩토리 메서드(Static Factory Method) 채택. `@Builder`는 내부에서만 사용.

---

### 검토한 방식 비교

| 방식                   | 설명                                  | 문제점                                          |
|----------------------|-------------------------------------|----------------------------------------------|
| `@Builder` 외부 직접 호출  | 외부에서 `Product.builder()...build()` 호출 | 필수 필드 누락을 컴파일 타임에 못 잡음. 어떤 조합으로든 객체 생성 가능    |
| 생성자 직접 호출            | `new Product(name, price, store)` 호출  | 파라미터 순서 의존, 의도 표현 불가, 수십 개 필드 시 가독성 급락       |
| **정적 팩토리 메서드** (채택)  | `Product.create(name, price, store)` 호출 | 없음. 생성 시점에 불변식 강제, 도메인 의도 표현 가능              |

---

### @Builder 문제점

- 필수 필드가 누락되어도 컴파일 타임에 오류가 발생하지 않는다. 런타임에 `NullPointerException`이나 잘못된 상태의 객체가 생성될 수 있다.
- 외부에서 어떤 조합으로든 객체를 생성할 수 있어, 도메인 불변식 보호가 불가능하다.
- Rich Domain Model 원칙과 충돌한다. 엔티티는 항상 유효한 상태를 유지해야 하는데, 빌더를 외부에 노출하면 이를 보장할 수 없다.

---

### 정적 팩토리 메서드 장점

- 메서드 이름이 도메인 의도를 표현한다. (`create`, `reserve`, `initiate` 등)
- 생성 시점에 불변식(Invariant)을 강제할 수 있다. 유효하지 않은 상태의 객체 생성을 원천 차단한다.
- `@Builder`는 내부에서만 사용하여 빌더의 편의성은 유지하면서 외부 노출을 차단한다.
- JPA용 `protected` 기본 생성자는 항상 필요하다. (`@NoArgsConstructor(access = AccessLevel.PROTECTED)`)

---

### 코드 예시

#### BAD — @Builder 외부 직접 호출

```java
// 컴파일은 되지만, price가 음수여도 객체가 생성됨. 불변식 보호 불가.
Product product = Product.builder()
        .name("사과")
        .price(3000)
        .build();
```

#### GOOD — 정적 팩토리 메서드 호출

```java
// 생성 시점에 검증이 이루어짐. 유효한 객체만 생성됨.
Product product = Product.create("사과", 3000, store);
```

#### 실제 구현 예시

```java
@Entity
@NoArgsConstructor(access = AccessLevel.PROTECTED)  // JPA용 기본 생성자
@Builder(access = AccessLevel.PRIVATE)              // @Builder는 내부에서만 사용
public class Product {

    private String name;
    private int price;

    @ManyToOne(fetch = FetchType.LAZY)
    private Store store;

    // 정적 팩토리 메서드 — 도메인 의도를 표현하고, 생성 시점에 불변식 강제
    public static Product create(String name, int price, Store store) {
        if (price < 0) {
            throw new IllegalArgumentException("상품 가격은 0원 이상이어야 합니다.");
        }
        return Product.builder()
                .name(name)
                .price(price)
                .store(store)
                .build();
    }
}
```

#### 도메인 의미를 가진 메서드명 예시

| 엔티티      | 정적 팩토리 메서드         | 의미              |
|----------|---------------------|-----------------|
| Product  | `Product.create()`  | 상품 등록           |
| Order    | `Order.reserve()`   | 주문 예약           |
| Payment  | `Payment.initiate()` | 결제 시작           |

## DTO 변환 규칙

**결정**:
- Entity → Response DTO: `ResponseDTO.from(entity)` 정적 팩토리 메서드
- Request DTO → Entity: Service에서 정적 팩토리 메서드 직접 호출
- 변환 위치: Service가 DTO를 반환, Controller는 그대로 반환

---

### 변환 방향별 결정 이유

| 방식                         | 결정     | 이유                                                  |
|----------------------------|--------|-----------------------------------------------------|
| `Entity.toResponse()`      | **금지** | Entity가 DTO(뷰 관심사)를 알게 되어 레이어 경계 위반                |
| `ResponseDTO.from(entity)` | **채택** | DTO → Entity 단방향 의존성 유지. Entity는 DTO를 모른다.           |
| `RequestDTO.toEntity()`    | **지양** | DTO가 Entity 생성 로직을 갖게 됨. 정적 팩토리 메서드와 역할이 중복된다.      |
| MapStruct                  | **미채택** | 설정 복잡, 개인 프로젝트 규모에 오버스펙                             |

---

### 변환 위치

**Service가 DTO 반환** 방식을 채택한다.

- Controller가 도메인 구조를 알 필요가 없다. Controller는 HTTP 관심사에만 집중한다.
- 3-Layered Architecture에서 보편적으로 사용되는 패턴이다.
- Service가 트랜잭션 범위 안에서 DTO 변환까지 완료하므로, 지연 로딩(Lazy Loading) 문제를 예방한다.

---

### 코드 예시

#### 1. ResponseDTO.from(entity) 구현 예시

```java
// ProductResponse.java — record를 사용하여 불변 DTO 구현
public record ProductResponse(
        Long id,
        String name,
        int price,
        int stock
) {
    // DTO가 Entity에 단방향으로 의존. Entity는 이 DTO를 모른다.
    public static ProductResponse from(Product product) {
        return new ProductResponse(
                product.getId(),
                product.getName(),
                product.getPrice(),
                product.getStock()
        );
    }
}
```

#### 2. Service에서 정적 팩토리 메서드로 Entity 생성하는 예시

```java
@Service
@Transactional
public class ProductService {

    public ProductResponse createProduct(ProductCreateRequest request) {
        Store store = storeRepository.findById(request.storeId()).orElseThrow();

        // RequestDTO.toEntity() 대신, Entity의 정적 팩토리 메서드를 Service에서 직접 호출
        Product product = Product.create(request.name(), request.price(), store);
        productRepository.save(product);

        return ProductResponse.from(product);  // Service가 DTO 변환까지 완료
    }
}
```

#### 3. Service가 DTO 반환 / Controller가 그대로 반환하는 전체 흐름 예시

```java
// ProductController.java — HTTP 관심사에만 집중. 도메인 구조를 알 필요 없음.
@RestController
@RequiredArgsConstructor
@RequestMapping("/api/products")
public class ProductController {

    private final ProductService productService;

    @PostMapping
    public ResponseEntity<ProductResponse> create(@RequestBody @Valid ProductCreateRequest request) {
        ProductResponse response = productService.createProduct(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(response);
        // Controller는 Service가 반환한 DTO를 그대로 반환. Entity를 직접 다루지 않는다.
    }
}
```

---

### 금지 사항

**DTO 변환에서 금지**
- `Entity.toXxx()` 형태의 DTO 변환 메서드 금지. Entity가 DTO(뷰 관심사)를 알게 되어 레이어 경계를 위반한다.
- Controller에서 Entity → DTO 변환 금지. DTO 변환은 Service의 책임이다.
- 외부에서 `@Builder` 직접 호출 금지. Entity 생성은 반드시 정적 팩토리 메서드를 통해서만 한다.
