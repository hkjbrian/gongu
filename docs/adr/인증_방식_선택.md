# ADR-003: 인증 방식 선택

- **날짜**: 2026-04-19
- **상태**: 승인됨

---

## 배경

Gongu는 4자 이해관계자(공급자·본사·매장·고객)를 지원하는 공구 이커머스 플랫폼이다. 일반 회원(고객)은 카카오 소셜 로그인만 제공하고, 매장 관리자는 이메일/비밀번호 로그인을 사용한다. 백엔드는 프론트엔드 분리형 SPA 또는 앱 클라이언트를 대상으로 REST API를 제공하는 구조다.

이 구조에서 카카오 OAuth2 인증을 어떻게 처리할지 결정이 필요했다. 구체적으로는 다음 질문에 답해야 했다.

- Spring Security의 OAuth2 Client 기능을 얼마나 활용할 것인가?
- 카카오 액세스 토큰을 누가 획득하는가? (프론트엔드 vs 백엔드)
- 인증 후 세션/JWT 중 어떤 방식으로 상태를 유지할 것인가?

---

## 결정

**프론트엔드가 카카오 SDK로 액세스 토큰을 획득한 뒤 백엔드에 전달하면, 백엔드가 직접 카카오 API를 호출하여 사용자 정보를 검증하고 자체 JWT(JSON Web Token)를 발급하는 방식을 채택한다.**

인증 흐름은 다음과 같다.

```
1. 프론트엔드  →  카카오 SDK로 카카오 액세스 토큰 획득
2. 프론트엔드  →  POST /auth/oauth2/login  { "accessToken": "..." }
3. 백엔드      →  카카오 /v2/user/me 호출로 사용자 정보 검증
4. 백엔드      →  신규 회원이면 자동 가입, 기존 회원이면 조회
5. 백엔드      →  자체 Access Token(JWT) + Refresh Token 발급 및 응답
```

매장 관리자는 카카오 로그인과 무관하게 `POST /auth/store/login` 엔드포인트에서 이메일/비밀번호 방식으로 별도 처리한다.

## 검토한 대안

### 대안 1: Spring Security OAuth2 Client (풀스택 방식)

백엔드가 OAuth2 Authorization Code Flow 전체를 처리하는 방식이다. 백엔드에 리다이렉트 URI를 등록하고, Spring Security가 카카오 인가 코드 요청·토큰 교환·사용자 정보 조회를 자동으로 수행한다.

**장점**
- Spring Security가 OAuth2 흐름 전체를 자동 처리하므로 구현 공수가 낮다.
- 보안 처리(State 파라미터, PKCE 등)가 프레임워크 레벨에서 지원된다.

**단점**
- 백엔드가 리다이렉트 URI를 직접 처리해야 하므로, 프론트엔드와 백엔드가 분리된 SPA/앱 구조에 부적합하다. 카카오 로그인 후 리다이렉트가 백엔드로 향하기 때문에 프론트엔드 라우팅과 충돌이 발생한다.
- `spring-boot-starter-oauth2-client` 의존성 추가 시 자동 설정이 많아지고, 불필요한 세션 관련 컴포넌트가 활성화된다.
- 카카오 소셜 로그인 하나를 위해 사용하기에는 설정 복잡도 대비 효용이 낮다(오버스펙).

**결론**: 제외.

---

### 대안 2: Spring Security + 커스텀 카카오 API 호출 + JWT (채택)

프론트엔드가 카카오 SDK로 액세스 토큰을 직접 획득하고, 백엔드는 해당 토큰을 받아 카카오 API를 호출하여 검증한 뒤 자체 JWT를 발급하는 방식이다.

**장점**
- 프론트엔드와 백엔드의 역할이 명확히 분리된다. 백엔드는 REST API만 노출하면 된다.
- SPA 및 모바일 앱 모두에서 동일한 방식으로 사용 가능하다.
- `spring-boot-starter-security`만 추가하면 되므로 의존성이 가볍다.
- 기존에 정의된 API 스펙(`POST /auth/oauth2/login`)과 일치한다.
- 자체 JWT를 발급하므로 이후 인증 처리(필터, 권한 검사)가 일관적으로 구성된다.

**단점**
- 카카오 API 호출 코드를 직접 작성해야 한다(RestClient 또는 WebClient 사용).
- 카카오 액세스 토큰 검증 로직(만료, 위변조)을 직접 처리해야 한다.

**결론**: 채택.

---

### 대안 3: Spring Security 없이 커스텀 필터 + JWT

Spring Security를 사용하지 않고 서블릿 필터와 JWT 라이브러리만으로 인증을 직접 구현하는 방식이다.

**장점**
- 의존성이 가장 가볍고, 구조가 단순하다.

**단점**
- CSRF 방어, CORS 설정, 인증/인가 필터 체인 등 보안에 필요한 요소를 모두 직접 구현해야 한다.
- Spring Security가 기본으로 제공하는 보안 기본값(Security Default)을 포기해야 하므로 실수 가능성이 높다.
- 추후 권한 제어(매장 관리자, 본사 어드민 등) 로직을 추가할 때 코드가 복잡해진다.

**결론**: 제외.

## 결과

### 의존성

```gradle
// 채택: Spring Security만 추가
implementation 'org.springframework.boot:spring-boot-starter-security'

// 불필요: OAuth2 Client 의존성 추가하지 않음
// implementation 'org.springframework.boot:spring-boot-starter-oauth2-client'
```

### 후속 조치

- `KakaoApiClient`: RestClient를 사용하여 카카오 `/v2/user/me` 호출 및 사용자 정보 파싱 담당.
- `JwtProvider`: 자체 Access Token(단기) 및 Refresh Token(장기) 발급·검증 담당. 비밀키는 환경변수로 관리.
- `JwtAuthenticationFilter`: 매 요청마다 Authorization 헤더의 JWT를 검증하고 `SecurityContext`에 인증 정보를 주입하는 OncePerRequestFilter 구현.
- `AuthService`: 카카오 사용자 정보 기반 신규 가입 또는 기존 회원 조회 후 JWT 발급 유스케이스 처리.
- 매장 관리자 로그인(`POST /auth/store/login`)은 `StoreAdminAuthService`에서 이메일/비밀번호 검증 후 동일한 JWT 발급 방식으로 처리.
- Refresh Token은 DB(또는 Redis)에 저장하여 재발급 및 로그아웃 시 무효화 처리.
