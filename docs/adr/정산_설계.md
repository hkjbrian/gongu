# ADR-008: 정산 설계 — 본사 → 매장

- **날짜**: 2026-08-31
- **상태**: 승인됨
- **관련 이슈**: #194

---

## 배경

주문·결제는 구현되어 있으나 **판매 대금을 매장에 정산하는 절차가 없다.** 결제금은 PortOne을 통해 전액 플랫폼(본사) 계정으로 입금되므로, 매장은 판매를 수행하고도 대금을 수취할 경로가 없는 상태다.

`docs/00-project-brief.md`는 이 서비스의 이해관계자를 **공급자·본사·매장·고객 4자**로 규정한다. 그러나 현재 시스템이 모델링한 것은 `stores`와 `users` 둘뿐이며, 공급자와 본사는 엔티티로 존재하지 않는다. 본사는 "시스템 그 자체"로 암묵적으로만 존재한다.

따라서 이 ADR은 **시스템이 모델링한 경계 안에서** 정산을 정의한다. 경계 밖의 정산은 「범위에서 제외한 것」에 명시한다.

### 실제 업무 흐름

```
1. 공급자 ↔ 본사     판매 협의 (수량·매입가)
2. 본사 ↔ 매장       매장별 재고 배분 (예: 80개)
3. 본사 → 매장       물류 발송
4. 고객 → 온라인 예약  end_at까지 (예: 60개 예약)
5. 매장 도착          잔여 20개는 오프라인 판매분
6. 고객 픽업
```

## 결정 1: 정산 방향 — 본사 → 매장

**온라인 예약 결제분에 한해, 본사가 매장에 지급해야 할 금액을 확정·기록한다.**

### 근거

코드가 이 방향을 강제한다.

| 사실 | 근거 |
|---|---|
| 결제금은 본사가 수취 | `payments.merchant_uid` / `imp_uid` 모두 플랫폼 소유. 매장이 결제금을 수취하는 경로가 없음 |
| 매장은 판매·픽업 거점 | `arriveOrder`를 `StoreAdmin`이 호출. 입고·픽업만 담당 |
| 상품은 매장에 귀속 | `products.store_id` — 매장별 배분 재고가 곧 공구 회차 |

### 방향이 둘인 이유와 그 처리

실제 업무에는 반대 방향도 존재한다. **오프라인 잔여 재고 판매(흐름 6번)는 매장이 대금을 직접 수취**하므로 `매장 → 본사` 납입이 발생한다.

그러나 **오프라인 결제 경로가 시스템에 없다.** 결제는 PortOne 온라인 단일 경로뿐이다. 따라서 이번 범위는 `본사 → 매장` 한 방향으로 한정한다.

---

## 결정 2: 정산 단위 — 매장 × 상품(공구 회차)

### 근거

- 공구는 **회차 단위로 열리고 닫힌다.** 회차마다 `start_at` / `end_at` / 도착일 / 픽업 기한이 모두 다르다
- `products.store_id`가 있으므로 **상품 한 건이 곧 매장별 회차**다. 별도 개념을 만들 필요가 없다
- 멱등 키가 `(store_id, product_id)` 하나로 단순해진다. 일자 단위였다면 정산 차수까지 키에 포함해야 한다

### 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 매장 × 일자 | 여러 회차가 한 정산에 섞인다. 회차마다 도착일이 달라 확정 시점(결정 3)이 회차별로 제각각이므로 집계 경계가 성립하지 않는다 |
| 주문 단위 | `orders`에 `store_id`가 없다. 매장 귀속은 `orders → order_items → products → stores` 3단 조인으로만 가능하다 |

## 결정 3: 정산 기준 시점 — `products.arrived_at` + 3일

**매장 도착 후 3일이 지난 회차를 정산 확정한다.**

### 환불 창과의 관계

```
도착(D)  ──────  D+2  ──────  D+3
  │              │            │
  │              │            └─ 정산 확정
  │              └─ 환불 마감
  └─ 픽업 시작
```

**환불 창을 먼저 닫고 하루 뒤에 정산한다.** 이 순서가 핵심이다 — 정산 확정 후 환불이 들어오면 이미 지급 확정한 금액이 틀어지며, 이는 정산에서 가장 피해야 할 상황이다. 시점을 이렇게 배치하면 그 상황이 **구조적으로 발생하지 않는다.**

### 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| `PAID` 시점 | 미수령·반품 리스크를 전부 플랫폼이 부담한다. `ARRIVED` / `RECEIVED` 상태가 정산에서 의미를 잃는다 |
| `RECEIVED` 시점 | 사용자가 수령 확인을 하지 않으면 영원히 정산되지 않는다. 미수령 건 처리 규칙을 별도로 만들어야 한다 |
| `end_at` 기준 | 물류 소요 시간이 반영되지 않는다. 물건이 매장에 도착하기도 전에 정산이 확정될 수 있다 |

### 선행 조건

**`products.arrived_at`이 현재 존재하지 않는다.** `Order`에 `receivedAt`은 있으나 `arrivedAt`은 없고, `arriveOrder`는 `bulkUpdateStatusByProduct`로 상태만 일괄 전이시킬 뿐 시각을 남기지 않는다. 이슈 #196에서 선행 처리한다.

입고는 상품(= 매장별 회차) 단위 이벤트이므로 `orders`가 아닌 `products`에 기록한다. 주문마다 기록하면 동일 값이 수백 건 중복된다.

## 결정 4: 매장 몫 — 도매가 방식 + 주문 시점 스냅샷

```
정산액(본사 → 매장) = (order_items.unit_price − order_items.supply_price) × quantity
```

### 근거

현재 스키마에는 **소비자 판매가(`products.price`) 하나뿐**이며, 매장 몫을 산출할 근거가 없다.

```
products.price        소비자 판매가      O 있음
판매자 → 본사 매입가    범위 밖           - Non-Goal
본사 → 매장 도매가      ???              X 없음  ← 정산이 막히는 지점
```

매장이 본사로부터 도매가로 공급받아 소매가로 판매하는 구조를 반영해 `supply_price`를 도입한다.

### 스냅샷이 필요한 이유

`docs/02-domain-rules.md`에 이미 다음 불변식이 있다.

> `OrderItem.unitPrice`는 주문 시점의 Product 가격 스냅샷이며 이후 변경되지 않는다.

도매가도 동일 원칙을 따른다. `products.supply_price`만 두면 **이후 도매가를 조정했을 때 과거 주문의 정산액이 소급 변경된다.** 따라서 `products.supply_price`(현재가)와 `order_items.supply_price`(주문 시점 스냅샷)를 모두 둔다.

`orders.total_price`는 정산 근거로 사용하지 않는다. 매장이 섞인 주문을 쪼갤 수 없기 때문이다(현재는 1주문 = 1상품이지만, 근거는 아이템 단위로 유지한다).

## 결정 5: 픽업 연장 건 — 다음 주기로 이월(carry-over)

픽업 날짜가 연장된 주문은 환불 창이 `arrived_at + 2일`을 넘긴다. **해당 주문 아이템을 그 회차 정산에서 제외하고 다음 주기로 이월한다.**

### 근거

| 대안 | 결과 |
|---|---|
| 회차 전체 정산을 연기 | 연장 한 건 때문에 **매장 전체 정산이 지연**된다 |
| 연장 건을 포함해 정산 | **정산 확정 후 환불**이 발생한다. 결정 3의 설계 의도가 무너진다 |
| **이월 (채택)** | 회차 정산이 제때 나가고, 연장 건은 자기 환불 창이 닫힌 뒤 별도 정산된다 |

`settlement_items`를 주문 아이템 단위로 두므로 이월 대상 표현이 자연스럽다.

**미해결**: 픽업 기한 연장을 저장할 필드가 아직 없다. 이슈 #199 착수 전에 결정한다.

## 결정 6: 배치 — Spring Batch를 도입하지 않는다

`@Scheduled` + `REQUIRES_NEW` 헬퍼 패턴으로 구현한다.

### 근거

- Spring Batch가 현재 의존성에 없다
- 기존 스케줄러 4종(`OrderExpiryScheduler`, `PaymentExpiryScheduler`, `ProductStatusScheduler`, `StockReconciliationScheduler`)이 **모두 동일 패턴**을 쓴다. 일관성을 깨뜨릴 이유가 없다
- 정산 대상이 매장별 회차 단위라 처리 건수가 작다. 청크·재시작·스킵 정책이 주는 이점보다 도입 비용이 크다

`StockReconciliationScheduler` / `StockReconciliationHelper` 구조를 그대로 따른다. 개별 회차 실패가 전체를 막지 않도록 건별 `REQUIRES_NEW` 트랜잭션으로 분리하고, 실패 시 `log.error` 후 계속 진행한다.

## 결정 7: 대사(reconciliation) — 내부 대사 우선, PG 전건 대사 제외

```
정산 대상 order_items 합계  vs  해당 주문들의 payments.amount 합계
```

### 근거

`PortOneClient`에는 `getPayment(paymentId)`와 `cancelPayment` 두 메서드만 있고 **결제 목록 조회 API가 없다.** 전건 대사를 하려면 결제 건마다 개별 HTTP 호출이 필요해 비용이 과다하다.

따라서 **내부 대사를 먼저 수행하고, 불일치가 발견된 건에 한해 `getPayment`로 개별 확인**한다.

### 불일치 시 처리

자동 보정하지 않는다. 정산 건을 `HELD`로 전이시켜 지급 대상에서 제외하고 사람이 확인한다.

이는 `StockReconciliationHelper`가 Redis 재고 과다 케이스에서 자동 보정 대신 `log.warn`만 남기는 것과 같은 원칙이다 — **금액이 걸린 불일치를 추측으로 보정하면 오차가 은폐된다.**

## 정산 상태 전이

```
PENDING ──> CONFIRMED ──> PAID_OUT
              │
              └──> HELD        (대사 불일치 — 사람 확인 필요)
```

- `PENDING` — 집계 완료, 확정 전
- `CONFIRMED` — 금액 확정. **이 시점 이후 해당 주문의 환불은 거부한다**
- `PAID_OUT` — 지급 완료 (실제 이체는 범위 밖. 상태만 관리)
- `HELD` — 대사 불일치로 보류

### 환불과의 경합 방지

환불 기한(D+2)과 정산 확정(D+3) 사이에 하루 여유가 있으나, 경계에서 겹칠 수 있다. **환불 요청 시 해당 주문이 이미 `CONFIRMED` 정산에 포함되었는지 확인하고 거부**하여 명시적으로 차단한다.

## 범위에서 제외한 것

| 항목 | 사유 |
|---|---|
| **오프라인 매장 결제 정산** | 결제 경로 자체가 시스템에 없다. 도입 시 `매장 → 본사` 역방향 정산이 추가로 필요하다 |
| **공급자 매입대금 정산** | `docs/00-project-brief.md`의 Non-Goal. 공급자가 엔티티로 존재하지 않는다 |
| **부분 환불 / 부분 정산** | `PortOneClient.cancelPayment(paymentId, reason)`에 금액 파라미터가 없어 전액 취소만 가능하다. 현재 1주문 = 1상품이므로 실질적 제약이 되지 않는다 |
| **실제 이체 연동** | "얼마를 지급해야 하는가"를 확정·기록하는 것까지가 범위다 |
| **PG 전건 대사** | 결정 7 참조 |
| **미수령 재고의 사후 처리** | 도착 +2일 경과 시 환불 불가이므로 대금은 수취하되 물건은 매장에 남는다. 폐기·반품 처리는 시스템 밖이다 |

## 결과

**긍정적 영향**

- 정산 확정 후 환불이 구조적으로 발생하지 않는다 (결정 3 + 상태 전이)
- 멱등 키가 `(store_id, product_id)` 단일 제약으로 끝나 재실행이 안전하다
- 도매가 스냅샷으로 과거 정산의 소급 변경이 차단된다
- 기존 스케줄러 패턴을 따르므로 코드베이스 일관성이 유지된다

**부정적 영향 및 제약**

- 집계 시 `order_items → products → stores` 3단 조인이 필요하다. `orders`에 `store_id`가 없기 때문이며, `order_items.product_id`·`orders.status` 인덱스를 확인해야 한다
- 이월 건은 정산 주기가 한 번 밀린다
- 대사 불일치가 자동 복구되지 않는다. 의도된 선택이지만 운영 부담이 된다

**선행 과제**

정산 구현 전에 아래가 선행되어야 한다.

| 이슈 | 내용 |
|---|---|
| #195 | 상품 상태 기계에 시간 축 누락 — `end_at` 경과 후에도 주문이 들어오면 어느 회차 정산에 넣을지 결정할 수 없다 |
| #196 | `products.arrived_at` 기록 — 정산 기준일과 환불 마감일의 근거 |
| #197 | 도매가 도입 및 주문 시점 스냅샷 — 정산액 계산 근거 |
| #198 | 도착 후 D+2 환불 — 결정 3의 전제 |

**향후 확장 경로**

- 오프라인 결제가 도입되면 `매장 → 본사` 역방향 정산을 추가한다. 정산 방향을 `settlements`의 속성으로 표현하면 같은 배치에서 처리할 수 있다
- 다중 상품 주문을 지원하게 되면 `order_items.status`가 필요해지고 부분 정산이 성립한다. `settlement_items`가 이미 아이템 단위이므로 스키마 변경은 최소화된다
