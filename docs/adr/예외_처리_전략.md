# ADR-004: 예외 처리 전략

- **날짜**: 2026-04-19
- **상태**: 승인됨

---

## 배경

Gongu는 REST API 서버로, 클라이언트가 에러 원인을 명확히 파악할 수 있어야 한다. 이를 위해 다음 문제를 해결할 예외 처리 전략이 필요했다.

- **도메인 예외와 인프라 예외의 혼재**: 재고 부족·상태 전이 불가 같은 도메인 규칙 위반과, PG사 통신 실패·카카오 API 오류 같은 외부 시스템 장애를 동일한 방식으로 처리하면 클라이언트가 원인을 구분하기 어렵다.
- **산발적인 try-catch**: 명시적인 전략 없이 개발하면 레이어마다 try-catch가 흩어지고, 에러 응답 형식이 일관되지 않는다.
- **클라이언트 분기 불가**: 에러 원인을 HTTP 상태코드나 자유 형식 메시지만으로 전달하면 클라이언트가 원인별로 다른 동작을 구현하기 어렵다.

---

## 결정

**계층형 예외 구조와 도메인별 ErrorCode enum을 조합하고, GlobalExceptionHandler 단일 지점에서 모든 예외를 에러 응답으로 변환하는 전략을 채택한다.**

### 1. 예외 계층 구조

```
RuntimeException
└── GonguException          ← 프로젝트 최상위 예외 (HTTP status, ErrorCode 보유)
    ├── BusinessException    ← 도메인 규칙 위반 (4xx)
    └── InfraException       ← 외부 시스템 장애 (5xx)
```

`GonguException`은 `ErrorCode`와 HTTP 상태코드를 함께 보유한다. `BusinessException`은 재고 부족, 주문 상태 전이 불가 등 도메인 규칙 위반 시 사용되며 4xx 응답에 대응한다. `InfraException`은 PortOne, 카카오 등 외부 시스템 장애 시 사용되며 5xx 응답에 대응한다.

### 2. ErrorCode 관리

에러 코드는 도메인별 enum으로 분리하여 관리한다.

- **분리 기준**: `UserErrorCode`, `ProductErrorCode`, `OrderErrorCode`, `PaymentErrorCode`, `AuthErrorCode`, `CommonErrorCode`
- **코드 형식**: `{도메인약어}_{3자리숫자}` (예: `PRODUCT_001`, `ORDER_002`, `AUTH_001`)
- **각 enum 값의 필드**: `code(String)`, `message(String)`, `httpStatus(int)`

모든 ErrorCode enum은 공통 `ErrorCode` 인터페이스를 구현하여 `GlobalExceptionHandler`에서 타입에 무관하게 처리할 수 있도록 한다.

### 3. API 에러 응답 형식

모든 에러 응답은 일관된 JSON 구조를 사용한다.

**단일 오류** (도메인 규칙 위반, 인프라 장애 등):

```json
{
  "code": "PRODUCT_001",
  "message": "재고가 부족합니다"
}
```

**유효성 검증 오류** (`@Valid` 실패 시):

```json
{
  "code": "COMMON_001",
  "message": "입력값이 올바르지 않습니다",
  "errors": [
    { "field": "quantity", "reason": "1 이상이어야 합니다" }
  ]
}
```

### 4. 레이어별 예외 처리 전략

| 레이어 | 역할 | 처리 방식 |
|---|---|---|
| **Entity** | 도메인 규칙 강제 | 규칙 위반 시 `BusinessException`을 직접 throw. try-catch 없음. |
| **Service** | 유스케이스 조율 | 대부분 예외를 그대로 전파. 외부 API(카카오, PortOne) 실패는 `InfraException`으로 변환 후 re-throw. 리소스 미존재(404)는 Repository 조회 후 throw. |
| **Controller** | 요청/응답 변환 | 예외를 직접 잡지 않음. `@Valid` 검증만 자동 처리. |
| **GlobalExceptionHandler** | 예외 → 응답 변환 | 모든 예외를 한 곳에서 처리. 아래 규칙에 따라 응답 반환. |

`GlobalExceptionHandler`(`@RestControllerAdvice`)의 처리 규칙:

- `BusinessException` → ErrorCode에 정의된 4xx 응답
- `InfraException` → ErrorCode에 정의된 5xx 응답
- `MethodArgumentNotValidException` → 400 응답 (`errors` 배열 포함)
- 그 외 `Exception` → 500 응답 (상세 메시지 클라이언트에 노출 금지, 로그에만 기록)

### 5. 예외 던지는 위치 원칙

- **도메인 규칙 위반**: Entity가 직접 throw. Rich Domain Model 원칙과 일치한다.
- **리소스 미존재(404)**: Service에서 Repository 조회 후 throw.
- **입력 유효성 오류**: Controller의 `@Valid`가 자동 처리.

## 검토한 대안

### 대안 1: 단일 Exception + String 메시지

예외를 단일 클래스로 통일하고, 에러 원인을 메시지 문자열로 전달하는 방식이다.

**단점**
- 클라이언트가 에러 코드로 분기할 수 없다.
- 메시지 문자열이 변경되면 클라이언트 코드도 함께 수정해야 한다.

**결론**: 제외.

---

### 대안 2: HTTP 상태코드만 사용

별도의 에러 코드 없이 HTTP 상태코드만으로 에러 원인을 전달하는 방식이다.

**단점**
- 같은 4xx 범위 내에서도 원인이 다양하여(재고 부족, 상태 전이 불가, 권한 없음 등) 클라이언트가 원인을 구분할 수 없다.

**결론**: 제외.

---

### 대안 3: 계층별 Exception + ErrorCode enum 분리 (채택)

도메인/인프라 계층을 분리한 예외 계층과 도메인별 ErrorCode enum을 조합하는 방식이다.

**장점**
- 클라이언트는 `code` 필드로 원인을 명확히 구분하고 분기할 수 있다.
- 서버는 레이어 역할에 맞게 예외를 다루며 산발적인 try-catch가 없어진다.
- `GlobalExceptionHandler` 단일 지점에서 일관된 에러 응답 형식을 보장한다.

**결론**: 채택.

---

## 결과

### 구현 대상 클래스

- `GonguException`: 프로젝트 최상위 예외 기반 클래스
- `BusinessException`: 도메인 규칙 위반 예외
- `InfraException`: 외부 시스템 장애 예외
- `ErrorCode`: 모든 ErrorCode enum이 구현하는 공통 인터페이스
- `UserErrorCode`, `ProductErrorCode`, `OrderErrorCode`, `PaymentErrorCode`, `AuthErrorCode`, `CommonErrorCode`: 도메인별 ErrorCode enum
- `GlobalExceptionHandler`: `@RestControllerAdvice` 기반 전역 예외 핸들러
- `ErrorResponse`: 에러 응답 DTO (`code`, `message`, `errors` 필드 포함)

### 후속 조치

- Entity 내부에서 예외를 throw할 때는 반드시 `BusinessException` 또는 그 하위 클래스를 사용한다.
- 5xx 응답 시 상세 메시지는 로그에만 기록하고, 클라이언트에는 generic 메시지를 반환한다.
- 신규 도메인이 추가될 경우 해당 도메인의 ErrorCode enum을 별도 파일로 생성하고 `ErrorCode` 인터페이스를 구현한다.
