# ADR-005: 재고 동시성 제어 전략

- **날짜**: 2026-05-09
- **상태**: 승인됨

---

## 배경

공구 상품은 `start_at` ~ `end_at` 기간 동안 판매된다. 판매 오픈 시점에 동일 매장의 여러 회원이 동시에 주문을 시도할 수 있으며, 이 때 `remaining_stock`(잔여 재고)을 정확하게 차감하지 못하면 **초과 판매(overselling)** 가 발생한다.

`products` 테이블에는 동시성 제어를 위해 `version` 컬럼(낙관적 락 후보)이 이미 정의되어 있다. 구현에 앞서 어떤 동시성 제어 전략을 채택할지 결정해야 했다.

---

## 결정

**비관적 락(Pessimistic Lock, `SELECT FOR UPDATE`)** 을 재고 차감의 동시성 제어 전략으로 채택한다.

`@Version` 필드는 엔티티에 선언하되 동시성 제어의 주 수단으로 사용하지 않는다. 비관적 락이 실패하는 예상치 못한 케이스에 대한 **보조 안전망** 역할로 유지한다.

---

## 결정 과정

### 1단계: 선택지 도출

재고 동시성 문제를 해결하는 방법으로 다음 네 가지를 검토했다.

| 방법 | 핵심 원리 |
|------|-----------|
| 낙관적 락 (`@Version`) | 충돌 감지 후 재시도 |
| 비관적 락 (`SELECT FOR UPDATE`) | 처리 전 선점 락 |
| Redis 분산 락 | Redis 키로 임계 구역 보호 |
| Redis 원자적 연산 + 메시지 큐 | Redis를 실시간 재고 주체로 분리 |

### 2단계: 극초고동시성 아키텍처 이해

쿠팡 타임딜 같은 수만~수십만 TPS 환경에서는 DB를 critical path에서 제거하는 것이 핵심이다.

```text
주문 요청 폭주
      ↓
Redis Lua 스크립트 (원자적 재고 차감)   ← 수십만 TPS, 즉시 응답
  ├─ 재고 부족 → 즉시 품절 응답
  └─ 재고 있음 → Kafka 발행
              ↓
       Kafka Consumer                    ← 순차 처리, DB 부하 조절
              ↓
       DB 재고 차감 + 주문 기록
```

이 구조에서 Redis는 **실시간 재고의 임시 주인**, DB는 **최종 상태의 영구 저장소**로 역할이 분리된다. 단, Redis 장애 시 DB에서 재고를 재적재해야 하고 최종 정합성(Eventual Consistency)을 허용해야 하는 복잡도가 따른다.

### 3단계: Redis 분산 락 단독 적용 검토

Redis 분산 락(Redisson 등)은 Redis 키로 임계 구역을 보호하는 방식으로, Kafka 없이도 DB 락의 대안이 될 수 있다. 그러나 단일 노드 MySQL이 병목이 아닌 현재 구조에서, Redis 외부 의존성 추가 비용(Redis 장애 시 락 해제 처리, TTL 설정, 클러스터 구성)이 비관적 락 대비 얻는 이점(DB 커넥션 절감)을 초과한다고 판단하여 제외했다.

### 4단계: 공구 서비스의 동시성 수준 평가

| 항목 | 공구 서비스 | 쿠팡 타임딜 |
|------|-------------|-------------|
| 동시 주문 주체 | 특정 매장 회원 (수십~수백명) | 전 국민 (수만~수십만명) |
| 충돌 빈도 | 오픈 시점에 집중, 이후 산발적 | 상시 극초고밀도 |
| 아키텍처 필요 수준 | DB 락으로 충분 | Redis + Kafka 필수 |
| 최종 정합성 허용 | 불필요 | 필수 |

Redis + Kafka 아키텍처는 현재 규모에서 **오버엔지니어링**이다. 도입 시 Redis 단일장애점 관리, Kafka Consumer 재처리, Redis↔DB 정합성 동기화 등의 운영 복잡도가 비용 대비 효과를 초과한다.

### 5단계: 낙관적 락 vs 비관적 락

두 전략의 근본적인 차이는 **충돌을 얼마나 자주 예상하는가**에 있다.

**낙관적 락의 전제**: "충돌이 드물다" → 충돌이 생길 때만 비용을 지불한다.

공구 오픈 시점에 N명이 동시에 주문하면:

```text
1라운드: N명 시도 → 1명 성공, N-1명 OptimisticLockException → 재시도
2라운드: N-1명 재시도 → 1명 성공, N-2명 또 실패 → 재시도
...
일부는 max retry 초과 → 주문 실패
```

재시도가 DB를 반복적으로 두드리면서 **부하는 증가하고 처리 시간은 예측 불가능**해진다. 사용자는 "재고가 있는데 왜 주문이 안 되지?"라는 경험을 하게 된다.

공구 오픈은 충돌이 **예외적 상황이 아니라 정상 상황**이다. 낙관적 락이 효율적인 조건(충돌 희소)과 반대된다.

**비관적 락의 전제**: "충돌이 빈번하다" → 처음부터 락을 잡고 순서대로 처리한다.

```text
N명 동시 시도 → 줄 세우기
→ 1번 처리 완료 → 2번 처리 → ... → N번 처리
→ 모두 1번의 시도로 성공 or 재고 부족 명확히 응답
```

재시도가 없고, 실패 이유가 명확하고("재고 부족"), 처리 시간이 예측 가능하다.

## 최종 비교

| 항목 | 낙관적 락 | 비관적 락 | Redis + Kafka |
|------|-----------|-----------|---------------|
| 충돌 가정 | 드물다 | 빈번하다 | 무관 |
| 충돌 시 처리 | 재시도 (DB 부하 증가) | 대기 후 처리 | Redis 원자적 차단 |
| DB 왕복 수 | 충돌 빈도 × N | 항상 1 | 0 (Redis 처리) |
| 처리 시간 예측 | 어려움 | 가능 | 가능 |
| 재고 부족 응답 | 재시도 후 실패 | 즉시 명확 | 즉시 명확 |
| 구현 복잡도 | 낮음 (재시도 로직 필요) | 낮음 | 높음 |
| 공구 서비스 적합성 | ✗ | ✅ | 오버엔지니어링 |

## 구현 방향

```java
// Repository: 비관적 락으로 상품 조회
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM Product p WHERE p.id = :id")
Optional<Product> findByIdWithLock(@Param("id") Long id);

// Entity: @Version은 보조 안전망으로 유지
@Version
private Long version;

// Entity: 재고 차감은 도메인 메서드로 캡슐화 (ADR-002 준수)
public void decreaseStock(int quantity) {
    if (this.remainingStock < quantity) {
        throw new BusinessException(ProductErrorCode.INSUFFICIENT_STOCK);
    }
    this.remainingStock -= quantity;
}

// Service: 락 획득 후 도메인 메서드 호출
@Transactional
public void order(Long productId, int quantity) {
    Product product = productRepository.findByIdWithLock(productId)
            .orElseThrow(() -> new BusinessException(ProductErrorCode.PRODUCT_NOT_FOUND));
    product.decreaseStock(quantity);
}
```

## 결과

**긍정적 영향**
- 재고 차감의 정확성 보장 (overselling 원천 차단)
- 재시도 로직 불필요 → 처리 흐름 단순
- 재고 부족 시 명확한 즉시 응답

**부정적 영향 및 제약**
- 동시 주문 수 증가 시 처리량(TPS)이 락 대기 시간에 비례해 감소
- 트랜잭션을 짧게 유지해야 함 (락 보유 시간 최소화)
- 외부 API 호출(결제 등)을 재고 차감 트랜잭션 내부에 포함해서는 안 됨 (트랜잭션 경계 원칙)

**향후 확장 경로**
서비스 규모가 커져 비관적 락으로 처리량이 부족해지면, Redis 재고 캐싱 계층을 추가하는 방향으로 단계적으로 전환한다. `@Version` 필드가 이미 존재하므로 전환 시 낙관적 락 경로도 열려 있다.
