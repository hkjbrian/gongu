# Code Review Guide

이 문서는 Codex 자동 PR 리뷰가 따라야 하는 기본 기준이다.

## 1. 리뷰 목적

- 버그 가능성, 회귀 위험, 테스트 누락, 설계 위반을 우선적으로 찾는다.
- 스타일 취향이나 사소한 취향 차이는 가능한 한 코멘트하지 않는다.
- "문제가 있을 가능성이 높다"는 근거가 분명할 때만 리뷰를 남긴다.
- 확신이 낮은 경우에는 인라인 코멘트보다 PR 요약 코멘트로 남긴다.

## 2. 리뷰 출력 원칙

- 실제 수정이 필요한 내용만 인라인 코멘트로 남긴다.
- 변경 라인에 직접 연결하기 어려운 설계 메모, 추가 질문, 추적 메모는 PR 요약 코멘트에 남긴다.
- 같은 근본 원인에서 나온 지적은 하나로 묶는다.
- 이미 PR 설명이나 기존 리뷰에서 충분히 다뤄진 내용은 중복하지 않는다.
- 가능한 한 "왜 문제인지"와 "어떤 식으로 고치면 되는지"를 같이 적는다.

## 3. 우선순위 기준

### Critical

- 데이터 손상, 권한 우회, 결제/정산 오류, 심각한 동시성 오류
- 운영 장애나 보안 사고로 바로 이어질 가능성이 높은 문제

### High

- 실제 동작 버그 가능성이 높음
- 예외 처리 누락으로 5xx 또는 잘못된 상태 전이가 발생할 가능성이 높음
- 기존 요구사항 또는 불변식을 깨는 설계 변경

### Medium

- 테스트 누락으로 회귀를 막기 어려움
- 컨벤션 위반으로 이후 기능 확장 시 버그를 유발할 가능성이 큼
- 책임 분리가 흐려져 유지보수 위험이 커지는 설계 문제

### Low

- 당장 오동작은 아니지만 추후 혼동을 만들 수 있는 구현
- 문서/설명/이름 불일치

## 4. 이 저장소 전용 기준

### 아키텍처

- 기본 구조는 `Controller -> Service -> Repository` 3계층을 유지한다.
- Service는 유스케이스 조율과 트랜잭션 경계 관리에 집중한다.
- Entity는 자신의 상태 전이와 불변식 검증을 스스로 책임진다.
- 여러 엔티티에 걸친 순수 계산은 Domain Service로 분리할 수 있다.

### Entity 규칙

- `public setter` 또는 외부에서 임의 상태 변경이 가능한 구조는 지양한다.
- Entity 안에서 Repository 주입, 외부 API 호출, 트랜잭션 관리 금지
- 상태 변경은 의미 있는 도메인 메서드로 드러나야 한다.
- 생성은 정적 팩토리 메서드 우선, 외부에 열린 `@Builder` 남용 금지

### Service 규칙

- Service가 getter로 값을 꺼내 비즈니스 판단 후 setter로 다시 넣는 패턴을 금지한다.
- 상태 검증과 상태 변경은 해당 Entity에 Tell 방식으로 위임한다.
- 여러 Entity를 조합하더라도 판단 로직까지 Service로 흘러들어오지 않게 본다.

### 테스트 기준

- 상태 전이, 예외 케이스, 동시성 제어, 금액/수량 계산 로직은 테스트가 특히 중요하다.
- 기능 추가나 버그 수정 PR인데 핵심 시나리오 테스트가 없으면 기본적으로 지적 대상이다.
- 테스트가 없더라도 PR 설명에 별도 사유가 충분히 적혀 있으면 요약 코멘트 수준으로 낮출 수 있다.

### 예외 처리

- 도메인 불변식 위반은 프로젝트 예외 전략에 맞는 `BusinessException` 계열 처리인지 본다.
- 에러 코드가 누락되거나 계층 책임에 맞지 않는 예외를 던지는지 확인한다.

## 5. 인라인 코멘트를 남기는 경우

- 변경된 라인에 바로 연결되는 버그 가능성이 있을 때
- 해당 라인이 직접적으로 컨벤션 위반을 만들 때
- 수정 지점이 비교적 명확할 때

## 6. PR 요약 코멘트로 남기는 경우

- 여러 파일을 함께 봐야 보이는 설계 이슈
- 테스트 전략 제안
- 확신은 있지만 단일 라인으로 고정하기 어려운 우려사항
- 변경 라인 밖에 원인이 있는 후속 점검 항목

## 7. 리뷰 톤

- 단정적 비난 대신 근거 중심으로 쓴다.
- "이유", "영향", "추천 방향" 순서가 드러나면 좋다.
- 불필요한 칭찬 남발보다 신호가 분명한 피드백을 우선한다.

## 8. LGTM 기준

아래 조건을 모두 만족하면 LGTM 또는 Approve 후보로 본다.

- Critical / High / Medium 수준의 미해결 이슈가 없음
- 필요한 테스트가 충분하거나, 테스트 생략 사유가 설득력 있음
- 프로젝트 아키텍처 및 도메인 모델 컨벤션을 위반하지 않음
- 기존 리뷰 스레드가 모두 해결됨
