# Gongu

> 공급자 · 본사 · 오프라인 매장 · 고객, 4자 이해관계자 구조의 공동구매(공구) 이커머스 웹 서비스

<br>

## 프로젝트 개요

**Gongu**는 기존에 카카오톡 단톡방으로 비공식적으로 운영되던 오프라인 매장의 공구 프로세스를 시스템화한 서비스입니다.

<br>

## 기존 방식의 문제점

| 문제 | 기존 방식 | 불편함 |
|------|-----------|--------|
| 공구 홍보 · 예약 | 카카오톡 단톡방 | 진행 중인 공구 물품을 한눈에 파악하기 어려움 |
| 예약 방식 | 카톡 메시지 전송 | 비정형 방식으로 인한 예약 오류 · 누락 발생 |
| 결제 · 수령 | 입고 후 오프라인 현장 결제 | 사전 결제 수단이 없어 노쇼 방지 불가 |

<br>

## 해결하는 문제

- 진행 중인 공구 상품을 **한눈에 확인**할 수 있는 리스트 제공
- 시스템화된 예약으로 **예약 오류 · 누락 방지**
- 사전 결제 도입으로 **노쇼 방지**

<br>

## 서비스 흐름

### 1단계 — 공구 개설

본사가 공급자에게 먼저 제안하거나, 공급자가 본사에 입점 제안을 할 수 있습니다.
양측이 공구 물품 · 수량 · 가격 조건에 **합의하면 공구가 확정**되고, 오프라인 매장에 등록되어 고객에게 공개됩니다.

```
공급자 ←──── 제안 / 협의 ────→ 본사
                                  │
                              합의 확정
                                  │
                                  ▼
                            오프라인 매장 등록
                                  │
                                  ▼
                            고객에게 공구 공개
```

### 2단계 — 공구 진행

고객은 진행 중인 공구 상품을 조회하고 **선착순으로 예약 및 결제**합니다.
목표 수량이 채워지거나 마감 기한이 되면 공구가 종료되고, 물품 입고 시 고객에게 알림이 발송됩니다.
수령이 완료되면 본사 · 매장 · 공급자 간 **정산이 자동 처리**됩니다.

```
고객 예약 · 결제
      │
      ▼
공구 마감 (선착순 or 기한)
      │
      ▼
물품 입고 → 고객 알림 발송
      │
      ▼
고객 수령 완료
      │
      ▼
본사 · 매장 · 공급자 정산
```

<br>

## 기술적 구현 목표

| 주제 | 내용 |
|------|------|
| 공구 합의 프로세스 | 본사 ↔ 공급자 간 제안 · 협의 · 확정 상태 관리 |
| 동시성 제어 | 선착순 마감을 위한 Redis 분산 락 + 낙관적 락 |
| 결제 트랜잭션 | PG 연동 및 장애 시 보상 트랜잭션 처리 |
| 주문 상태 머신 | 예약 → 결제 → 입고 → 수령 상태 전이 관리 |
| 서킷브레이커 | Resilience4j 기반 PG 장애 전파 방지 |
| 정산 배치 | Spring Batch 기반 월별 정산 및 이중 정산 방지 |
